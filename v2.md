# Paint Dealer Visualizer v2 — Product & Engineering Specification

**Role framing for the build agent:** You are acting as a Principal Product Designer, Staff Frontend Engineer, and Solutions Architect. Do not scaffold a demo — produce the architecture and code a paid SaaS product would ship.

**Current state (v1):** A single-page, four-step linear wizard (Upload → Clean up → Select surface → Apply color) with no project concept, no persistence, a flat 30-swatch color grid, and a manual brush-then-apply flow. Nothing survives a refresh.

**Target state (v2):** A project-centric AI visualization platform for paint dealers, structurally comparable to Figma/Canva for the canvas experience and to a lightweight CRM for the business-record side.

---

## 1. Product Vision & Non-Goals

**Vision:** A dealer opens the app, sees their book of client projects, opens one, and gets a persistent, undo-capable, multi-layer photo workspace where they can mask surfaces, try catalog colors in real time, generate AI suggestions, and export a client-ready comparison — without losing work on refresh, tab close, or crash.

**Explicit non-goals for this release** (call these out so scope doesn't creep):
- No multi-user real-time co-editing (single editor per project for v2; design the data model so it *could* support it later, but don't build presence/CRDT sync now).
- No native mobile app — responsive web only, with a reduced-capability tablet/touch mode for the canvas.
- No custom paint-mixing/spectrophotometer integration in this phase.
- No offline-first guarantee beyond draft autosave (see §7) — full offline mode is a future phase.

---

## 2. Personas

1. **Dealer Rep (primary user):** Visits client homes/sites, takes photos, generates visualizations on a laptop or tablet during or after the visit. Needs speed and low friction more than deep photo-editing power.
2. **Store Manager:** Reviews projects across reps, checks catalog usage, pulls reports. Needs Dashboard and Reports, rarely touches the Visualizer.
3. **Admin:** Manages the paint catalog (SKUs, brands, finishes, pricing), user roles, and brand/store settings.

Design the IA and permissions (§10) around these three, not a single undifferentiated "user."

---

## 3. Information Architecture

Top-level nav (persistent left rail, collapsible):

- **Dashboard** — recent projects, quick-create, usage stats, "continue where you left off" (last 3 opened projects with thumbnail + last-edited timestamp).
- **Projects** — searchable/filterable list (by client, status, date, rep). Grid and table view toggle. Status states: `Draft`, `In Review`, `Client Approved`, `Archived`.
- **Paint Catalog** — searchable card library (§6), admin-editable if role permits.
- **Visualizer** — opens *only* in the context of a project (no orphaned edits). Route shape: `/projects/:projectId/visualize`.
- **Reports** — catalog usage frequency, most-visualized colors, project completion funnel, export counts.
- **Settings** — org profile, brand/store info, user roles, catalog import (CSV/API), API key management if applicable.

**Key IA rule:** the Visualizer is never a standalone destination. Every canvas session is scoped to a `Project`. If a user lands on `/visualize` with no project, redirect to a "new project" creation modal that asks for a client name (minimum) before proceeding — this guarantees every asset has a home.

## 4. Data Model

Define these entities explicitly (this is the backbone the rest of the app hangs off of). Use these as the persisted schema, whether backend-side (Postgres/REST) or local (IndexedDB) — see §7 for the sync strategy.

```
Project
  id, name, clientName, status, createdBy, createdAt, updatedAt
  coverAssetId (thumbnail reference)
  tags[]

Asset               // an uploaded photo and its derived states
  id, projectId, kind: 'original' | 'cleaned'
  originalFileRef, cleanedFileRef
  width, height, exifOrientation
  createdAt

Layer               // one per paintable surface region within an asset
  id, assetId, name (e.g. "Front wall", "Trim", "Roof")
  maskData (RLE-encoded or PNG alpha mask reference — see §6.2)
  createdVia: 'brush' | 'magic-wand' | 'lasso' | 'rect' | 'polygon' | 'ai-surface'
  currentColorId (nullable)
  opacity, finishOverride (nullable)
  order (z-index)
  locked: boolean, visible: boolean

PaintColor          // catalog entry, org-scoped
  id, sku, name, brand, finish, hex, lrv (light reflectance value, optional)
  isFavorite (per-user), lastUsedAt (per-user)

HistoryEntry        // undo/redo stack, persisted per project
  id, projectId, timestamp, actorId
  action: 'mask-created' | 'color-applied' | 'layer-deleted' | ...
  beforeState (diff or snapshot ref), afterState

Concept             // a saved "look" — a named snapshot of layer/color state
  id, projectId, name, thumbnail, layerColorMap, createdAt

ExportJob
  id, projectId, format: 'pdf' | 'png' | 'side-by-side-jpg'
  comparisonMode: 'side-by-side' | 'slider' | 'split' | 'fade'
  status: 'pending' | 'ready' | 'failed', fileRef
```

**Why this matters:** the original prompt said "everything must belong to a project and persist," but didn't define what "everything" is structurally. Layers-with-masks-with-colors is the actual unit of work in a paint visualizer — treat masks as first-class, reusable, re-colorable objects, not a one-shot "apply and flatten" operation. This is what enables live repainting instead of the current select-then-apply round trip.

## 5. Visualizer Workspace

### 5.1 Layout
- **Center canvas:** Konva `Stage`, pan (space+drag or two-finger), zoom (ctrl/cmd+scroll, pinch, and a persistent zoom control with fit-to-screen and 100% buttons), fullscreen toggle that hides all chrome.
- **Left sidebar (tabbed):** Assets (original/cleaned thumbnails) · Layers (reorderable list, visibility/lock toggles, per-layer color swatch) · History (scrubbable, click to preview a prior state without losing current state — "peek," not destructive jump, until confirmed) · AI Suggestions.
- **Right inspector (contextual — changes based on active tool):**
  - Tool = paint/select surface → Paint Catalog panel (§6)
  - Tool = brush/spray → brush size, hardness, opacity sliders
  - Tool = any selection tool → surface properties (name the layer, set finish override)
  - Always-present footer: Export controls
- **Floating toolbar:** vertical, icon + label on hover, tool group order: Selection tools (Magic Wand, Lasso, Rectangle, Polygon, AI Surface Selection) → Paint tools (Brush, Spray, Bucket Fill) → Utility (Eyedropper, Pan/Hand, Zoom).

### 5.2 Tool Behavior & Masking Architecture
This is the part most likely to get hand-waved — be explicit:

- Every selection tool (Magic Wand, Lasso, Rect, Polygon, AI Surface Selection) produces a **mask**, not an immediate paint action. The mask becomes a new `Layer` shown in the left sidebar, initially unpainted or previewed at low opacity.
- **Bucket Fill** = apply color directly to an existing selected mask/layer.
- **Brush/Spray** = two modes, and the tool options must make the mode explicit to the user:
  1. *Mask-editing mode* — refine an existing layer's mask (add/subtract with alt-key or toggle).
  2. *Direct-paint mode* — freehand color directly onto canvas, auto-generating a layer from the stroke.
- **AI Surface Selection** — calls the backend segmentation endpoint (preserve/extend the existing "AI color suggestions" API surface), returns candidate surface masks (wall, trim, roof, door), user picks one or accepts all, each becomes a `Layer`.
- **Live painting requirement from the original prompt** ("must update live," "replace Select→Apply"): implement via Konva `Group` compositing — each layer is a shape with a mask (via `globalCompositeOperation` or a cached mask sprite) and a fill color bound directly to Zustand state. Changing `currentColorId` on a layer re-renders that layer only (not the whole canvas), so color swaps are instant with no "Apply" click.
- Store masks as compressed alpha PNGs (or RLE for simple polygon/rect shapes) referenced by URL/blob, not inline base64 in app state — keeps Zustand store small and undo snapshots cheap.

### 5.3 Undo/Redo
Implement as a command pattern, not full-state snapshots: each `HistoryEntry` stores enough to invert the action (e.g., "layer X mask changed from A to B"). This keeps history scrubbing (§5.1) cheap and makes the persisted `HistoryEntry` table in §4 meaningful rather than a memory-only stack that dies on refresh.

## 6. Paint Catalog

### 6.1 Card & Search Requirements
Replace the swatch grid with cards showing: color preview, name, SKU, finish, brand, favorite toggle (per-user, persisted), recently-used rail (last 8, per-user, per-org). Search/filter by name, SKU, brand, finish, and hex-proximity ("colors like this one"). Instant hover preview must apply the color to the *currently active layer* in the canvas at low latency (<100ms) without committing it — commit only on click.

### 6.2 AI Suggestions
Preserve the existing "Suggest colors from photo" endpoint contract if possible; extend its response to be layer-aware (suggest per-surface, e.g., "wall: warm greige, trim: soft white" rather than one flat palette for the whole image) so suggestions map directly onto the Layer model in §4.

## 7. Persistence Strategy

Be concrete — "must persist" alone isn't buildable:

- **Source of truth:** backend (existing APIs, extended per §9). All entities in §4 are persisted server-side.
- **Autosave:** debounce local edits (e.g., 800ms after last action, or every 5th history entry, whichever first) and PATCH the project. Show a subtle "Saved" / "Saving…" / "Unsaved changes — retrying" indicator in the top bar — never a blocking save action.
- **Local draft cache:** mirror in-progress state to IndexedDB (via a Zustand persist middleware) keyed by `projectId`, so a refresh mid-edit restores instantly from local cache while the backend sync catches up, rather than showing a blank canvas during the fetch.
- **Conflict handling:** last-write-wins is acceptable for v2 given single-editor scope (§1), but the PATCH should include an `updatedAt` check and surface a non-blocking toast if a conflict is detected ("This project was updated elsewhere — reload to see the latest") rather than silently overwriting.
- **What must survive a refresh, explicitly:** original + cleaned image, all layers with their masks and assigned colors, undo history, saved Concepts, active tool/inspector state (nice-to-have, not required).

---

## 8. Comparison & Export

- Modes: **Original / Cleaned / Painted** as named states; **Side-by-side**, **Slider**, **Split view**, **Fade transition** as display modes for comparing any two of those states (e.g., Cleaned vs. Painted, or Painted-Concept-A vs. Painted-Concept-B if multiple `Concept`s exist).
- Export produces an `ExportJob` (§4): PDF (client-ready, with dealer branding header if configured in Settings), PNG, or side-by-side JPG. Export must run as an async job with a visible progress state, not a blocking spinner over the whole canvas — the user should be able to keep editing while an export renders.

---

## 9. Backend/API Contract

Preserve existing endpoints where they map cleanly (upload, clean-up, AI color suggestion). Extend with:
- `POST /projects`, `GET /projects`, `GET /projects/:id`, `PATCH /projects/:id`
- `POST /projects/:id/assets` (upload original)
- `POST /assets/:id/clean` (existing clean-up call, now asset-scoped)
- `POST /assets/:id/layers` (create layer from mask), `PATCH /layers/:id` (color/opacity/order changes)
- `POST /assets/:id/ai-surfaces` (layer-aware AI suggestion, §6.2)
- `POST /projects/:id/history` (append-only), `GET /projects/:id/history`
- `POST /projects/:id/exports`, `GET /exports/:id` (poll or webhook for job completion)

If the existing backend can't reasonably support project/layer scoping yet, flag this explicitly as a required backend migration rather than faking it client-side — don't let the frontend silently invent persistence that the backend doesn't actually back up.

## 10. Roles & Permissions

Minimum viable RBAC for the three personas in §2:
- **Rep:** create/edit own projects, use Visualizer, export.
- **Manager:** everything a Rep can do across *all* reps' projects, plus Reports.
- **Admin:** everything above, plus Paint Catalog management and Settings (org/brand config, user roles).

Gate nav items and API calls accordingly; don't just hide UI without server-side enforcement.

## 11. Technology & Engineering Standards

**Stack (as specified):** React, Tailwind CSS, shadcn/ui, Radix UI, Framer Motion, TanStack Query, Zustand, Konva.js.

**Usage boundaries:**
- **TanStack Query** owns all server state (projects, catalog, history reads, export job polling). **Zustand** owns ephemeral/local editor state (active tool, canvas viewport, in-progress mask before commit, undo stack pointer). Don't let these overlap — server data doesn't belong in Zustand, and transient UI state doesn't belong in Query cache.
- **Framer Motion** used only for meaningful state transitions (panel open/close, layer reorder, modal enter/exit) — no decorative motion, no animating things that don't change state.
- **Konva.js** canvas performance: use layer caching (`.cache()`) for static masks, avoid re-rendering the full stage on every color change (§5.2), and virtualize/lazy-load high-res source images (downscale for on-screen editing, keep full-res reference for export).

**Code quality bar:**
- No placeholder components, no `TODO` left in shipped code, no unused generated boilerplate.
- Modular by feature (`/features/visualizer`, `/features/catalog`, `/features/projects`) not by type (`/components`, `/hooks` dumped flat).
- Every async action (upload, clean-up, AI suggestion, export) has explicit loading, error, and empty states — no silent failures.

## 12. Accessibility & Responsive Design

- Full keyboard access to toolbar (tool shortcuts: B=brush, M=magic wand, L=lasso, etc.), inspector, and catalog search — canvas manipulation itself (freehand painting) is inherently mouse/touch-first, but tool *selection* and *color application* must be keyboard-operable (e.g., select a layer via keyboard, open catalog, arrow through cards, Enter to apply).
- ARIA live region announcing save status and export completion.
- Color contrast per WCAG AA across all UI chrome (catalog color swatches themselves are exempt as they represent real paint colors, not UI state).
- Responsive breakpoints: full three-pane layout ≥1280px; collapse left sidebar to an icon rail and right inspector to a slide-over sheet on tablet (768–1279px); Visualizer is read/compare-only below 768px (editing tools disabled with a clear message, not silently broken) — call this out as an intentional constraint, not a bug.

---

## 13. Reports (minimum viable)

- Catalog usage: most-applied colors/finishes org-wide and per-rep, over a selectable date range.
- Project funnel: counts by status (`Draft` → `In Review` → `Client Approved`), average time-in-status.
- Export activity: exports by format, by rep, over time.

---

## 14. Acceptance Criteria (what "done" means)

- [ ] A user can create a project, upload a photo, clean it, generate 3+ masked layers via at least two different selection tools, assign catalog colors to each, refresh the browser, and see the exact same state restored.
- [ ] Changing a layer's color updates the canvas with no visible "apply" step and no full-canvas re-render lag on a 4K source image.
- [ ] Undo/redo works across a session and history entries are visible/scrubbable in the left sidebar.
- [ ] A side-by-side and a slider comparison can both be generated and exported to PDF without blocking further edits.
- [ ] A Manager role can view Reports and all reps' projects; a Rep role cannot access another rep's project by direct URL manipulation (server-enforced, not just hidden nav).
- [ ] Full workflow is completable on a 1280px+ laptop and functionally usable (if visually reduced) on a 768px tablet.

---

## 15. Explicit Migration Note

If v1 has existing users/data mid-flight, define (even briefly) how existing wizard sessions map into the new Project/Layer model — e.g., a one-time migration script that wraps each legacy upload+applied-color result into a single-project, single-layer record — rather than leaving v1 data orphaned when v2 ships.
